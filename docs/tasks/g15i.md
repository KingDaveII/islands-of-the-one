# G1.5i: the room texture breaks after the first room, and a build label in the menu

Read CLAUDE.md, `docs/design/sprites.md` ("Tiles") and `docs/DEPLOY.md`, then `apps/client/src/render/roomTiles.ts`, `apps/client/src/render/world.ts` (the room build), `apps/client/Dockerfile`, `.github/workflows/deploy-staging.yml` and `apps/server/src/app.ts` (`/health`).

Work on the branch `g15i-room-texture-version`, which already holds this file (`docs/tasks/g15i.md`). Merge the latest `main` into it first. Open one PR, "G1.5i: room texture per room, build label", through the REST API (`gh pr create` is blocked).

## 1. The bug: rooms after the first draw clipped

**What David sees** in the M1 playtest at B, often:
- the floor stops short;
- the Kindled and the Husks fight on what looks like the Hollow;
- walls are invisible where the drawing is missing;
- the open door floats in the dark;
- the player seems to clip out of the map.

The sim is fine. Collision and positions match the room, but the drawing doesn't.

**MAIN's diagnosis, to confirm first:**
- `TileRoom.build` creates its RenderTexture once, at the first room's size.
- Every later room calls `rt.resize(w, h)` on it. In our Phaser version, resizing a RenderTexture doesn't grow the area that `batchDrawFrame` draws into. Possibly only the texture is resized and not the frame, or the RT's internal camera.
- So a room larger than the first in either direction is cut off at the first room's width or height.
- G1.5e's check missed it because each screenshot was a fresh run of one room (`startRun(seed, weapon, [room])`), never a room change.

**First:** reproduce it. Run a three-room run, with the autopilot or `startRun` and several templates, where a later room is wider or taller than the first. After each room change, compare the room texture (`roomImage()`) with the pipeline's drawing of the same template. Report the sizes you find before fixing anything.

**The fix:**
- Make each room's texture match its room exactly. The simplest route is to destroy the old RenderTexture and create a new one per room. If you fix `resize` instead, say why it's safe.
- Doors are already rebuilt per room. Check that nothing else built once, at the first room's size, is reused: the camera bounds, the clamp, the hollow margin, the debug overlay.
- Check for a leak too: a texture created per room must free the old one's GPU texture. Destroy it, and say how you checked.

**Tests:**
- A client test, or a headless browser check in `tools/screenshots-g15.mjs`, that runs a room change into a wider room and into a taller room. The texture's size must equal `cols × 32` by `rows × 32` every time, and the picture must equal the pipeline's for that template, pixel for pixel, as G1.5e compared one-room runs.
- Make it part of what runs in `pnpm check` if it can run headless there. If it can only run in the screenshot tool, say so, and add a `--room-changes` mode that fails loudly.

## 2. A build label on the start screen

David can't tell an old deploy from a new one when he playtests. Add a small build label.

- **Content:** the client's build as the first 7 characters of the commit SHA, plus the build date (UTC, `YYYY-MM-DD HH:MM`). Example: `build 8443ba3 · 2026-10-17 12:40`. In `pnpm dev` it reads `build dev`.
- **Plumbing:**
  - The deploy workflow already passes `APP_VERSION` (the full SHA) to the server image.
  - Pass it, and a build time, into the client image too: an `ARG` in `apps/client/Dockerfile`, then into Vite at build time (`import.meta.env` or a `define`).
  - Never put anything secret in it.
- **The server's build:** `/health` already returns `version`. If the client can read it (same origin), show it when it differs from the client's, for example `build 8443ba3 · server 19ef73d`. A mismatch is exactly what David needs to see. If `/health` can't be reached, show the client's build only, without an error.
- **Where:**
  - bottom-right corner of the start screen, and of the account screen if that's the first screen;
  - on the UI grid, as BitmapText through `label()` or `body()`;
  - in a muted UI colour token from `palette.ts`;
  - inside M1's safe margins, so it doesn't fight the menu.
  - It only uses characters the atlases have (`DRAWABLE_CHARS`); check `·` and `:`, or use `-` and `.`.
- **Also expose it as `window.__iot.build`** for playtests and screenshots.
- **Docs:** one line in `docs/DEPLOY.md` saying where the label comes from and how to check a deploy with it.
