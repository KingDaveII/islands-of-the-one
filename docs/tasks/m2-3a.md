M2 Task 3 (the holding) is split in two:
- **3a, this task:** where items are. That covers the purse, the pack, the holding store and the station baskets, the move between them, and the inventory screen.
- **3b, next:** the holding scene itself: walking, the stations, the active action, XP and offline progress. Its output lands in the baskets this task defines.

## Why

M2 Task 2 gave every Kindled one balance per item. GAME DESIGN's M2 numbers need items in **places**:
- **Purse:** gin lives here. It takes no slot and is never lost.
- **Pack:** what a Kindled carries abroad. It has 20 slots, and death costs only what is in it.
- **Store:** the holding store by the Writ post. It has unlimited slots and 9,999 per stack, and is reachable only on the holding.
- **Basket:** each station has one. Everything a station makes lands there until the player takes it to the store.

## Decisions (MAIN)

### 1. Places

Every item a Kindled holds is in exactly one place:

| Place | Holds | Limit |
|---|---|---|
| `purse` | currency only (`sealed-gin`) | the item's `stackLimit` (unlimited today) |
| `pack` | everything but currency | 20 slots in all. Each item takes `ceil(quantity / slotSize(kind))` slots. `slotSize`: material 50, sparkglass 99, consumable 5 |
| `store` | everything but currency | one stack per item, up to `storeLimit(kind)`: material 9,999. Sparkglass is unlimited, as its `stackLimit` is today |
| `basket:<stationId>` | what that station makes | none here; 3b decides what a basket holds |

- **Data:** these numbers go in a new `packages/shared/data/inventory.json` (`packSlots`, `slotSize` and `storeLimit` by kind), validated on load like `items.json`. They are GAME DESIGN's starting values, and pass 3 may change them.
- **Pack slots are derived, not stored.** The pack shows its items in `items.json` order, each split into full slots and then the remainder, so there's no manual arrangement to persist.
- **A store full of one item:** GAME DESIGN's toast "Store: twisted logs full." reads as one stack per item. If "unlimited slots" meant several 9,999 stacks of the same item, that's a data change later; say so in the PR.

### 2. The tables: expand-only

`items` has a unique key on (Kindled, item), so it can't hold one row per place. Do this:
- **A new table, `item_stacks`:** (Kindled, item, `place`, quantity), unique on (Kindled, item, place), with `quantity >= 0`, cascading with the Kindled. `place` is text validated by a shared guard (`purse`, `pack`, `store`, `basket:<stationId>` with a kebab-case id).
- **The migration copies `items` into it.** Currency goes to `purse`, everything else to `store`.
- **`items` is retired:**
  - no code reads or writes it;
  - it stays in `tables.ts` marked retired, per CLAUDE.md;
  - it's dropped in a later contract migration.

  A rollback to Task 2's code would read the stale `items` copy. That's acceptable on staging, which holds no real players; say so in the PR.
- **`item_ledger` gains a nullable `place` column.** Old rows keep null, meaning the Task 2 single balance. `balance_after` is now the balance of that place.
- **Lock order** becomes Kindled id, item id, place, all `collate "C"`.
- **Idempotency:** the unique ref key becomes (ref, Kindled, item, place). It must be a new index; keep the old one until the contract migration only if keeping it can't refuse a valid set. Otherwise replace it, and say which you did.
- **The boundary rules stay:** only the inventory module touches these tables (ESLint and `inventory-boundary.test.ts`). Extend both to `item_stacks`.

### 3. `inventory.apply` with places

- **A change** is `{ kindledId, itemId, place, delta }`. Each (Kindled, item, place) appears at most once in a set.
- **New refusals** (the whole set is refused, as now):
  - `wrong-place`: currency outside `purse`, or anything else in `purse`;
  - `pack-full`: the pack's derived slots would go over `packSlots`;
  - `stack-limit`, extended: a store stack over `storeLimit`.
- **A new reason, `move`:** a move is one set with −n from one place and +n to another, so the ledger shows both sides.
- **`apply` can run inside a caller's transaction** (an optional `tx`), so 3b can settle an action and its items in one transaction. Keep the standalone form.
- **The concurrency tests on real Postgres** (`inventory.postgres.test.ts`) gain:
  - moves racing between pack and store, with no deadlock and totals kept;
  - a pack-full race: two moves that each fit alone but not together, so exactly one wins.

### 4. The API (`packages/shared/src/api.ts`)

- **`GET /api/inventory`** answers by place:
  - `{ purse, pack, store, baskets }`;
  - each a list of `{ itemId, quantity }` in `items.json` order, and `baskets` keyed by station id.

  Bump `PROTOCOL_VERSION` if this breaks Task 2's shape, and update the client.
- **`POST /api/inventory/move`** takes `{ itemId, from, to, quantity }`.
  - Allowed between `pack` and `store`, both ways.
  - Allowed from a `basket:*` to `store` ("take all" in 3b).
  - Nothing else moves by this route: the purse is never a move target.
  - The Kindled comes from the session cookie only.
  - The guard refuses unknown fields and non-positive or non-integer quantities. Clamp nothing silently.
  - It answers the new inventory, or one of the error codes:
    - `pack-full`;
    - `stack-limit`;
    - `insufficient`;
    - `wrong-place`;
    - `bad-request`.
- **Being on the holding:** the store is reachable only there. M2 has no other place the Kindled can be, since the M1 run is a client-side test, so the server allows store moves always. Put the check in one function, `canReachStore(kindled)`, that returns true today, with a comment that voyages (M3) make it real.
- **The grant CLI** takes an optional place: `inv:grant <user> <item> <qty> [place]`. The default is `purse` for currency and `store` for everything else.

### 6. The inventory screen

Rebuild `InventoryScene` from the text list into GAME DESIGN's screen. It uses placeholder UI drawn with the existing panel style and BitmapText; ART's M2 UI kit replaces the look later, not the layout logic.
- **Two panes:**
  - the **pack**, a 5 × 4 grid of slots, each showing an icon placeholder (the item's initials) and its count;
  - the **store**, a scrolling grid.
- **Tabs filter both panes:** all, materials, Sparkglass, consumables, lore objects. The empty kinds show empty. The Words tab comes with word tiles in Task 5.
- **The header** shows the purse (gin) and the Sparkglass totals across pack and store: wild slivers, humming glass, deep glass.
- **The two consumable slots** (Q / F) sit under the pack. M2 has no consumable items yet, so they show empty and accept nothing; wire the assignment when consumables exist.
- **Moving items:**
  - Mouse: click moves the stack, right-click moves one, drag moves the stack.
  - Pad: Cross moves the stack, Square moves one, and the D-pad or left stick moves focus.
  - Touch: tap moves the stack, long-press moves one.

  Every move is a `POST /api/inventory/move`. The screen updates from the answer, never optimistically. A refusal shows the reason in one line ("Pack full.").
- **The tooltip** appears on hover or focus and takes no input:
  - the name;
  - the kind line (`Material · Mining`, or just the kind when there's no skill);
  - the card text in a muted style under a 1 px divider;
  - the count in this pane.
- **Opening:**
  - I on the keyboard, the Touchpad on a DualSense, and the existing start-screen button;
  - Esc, Circle or I closes it.
  - Add the binding to `packages/shared/data/controls.json` with the others; never hard-code it.
- **Nothing can be destroyed:** there is no delete or drop anywhere.
